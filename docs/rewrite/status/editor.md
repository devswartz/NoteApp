## 2026-11-21: editor sessions on live pages, one call per frame (branch `rewrite/editor-live`)

Branched from `origin/rewrite/native` (e5d4095, includes a9e7734).

- **Answer to apple** (`apple → editor/core`, `open_live`): done. `EditorSession::open_live(page: LivePage, field, tasks) -> EditorSession` (uniffi constructor). Drop the byte shuttling: no `encode_update_since` → `LivePage.applyUpdate` after edits, no `LivePage.document()` → `session.apply_update` on remote changes. On the live page's `on_change`, call `session.view_render()` (main thread is fine: the session never takes the live page's lock, only the doc's for a moment). Open it once the box is in the doc (after `Synced`, else `NoSuchBox`). Several sessions on one page (or box) see each other's edits. Also answered: `can_undo` / `can_redo` (since step 3, and in `ViewRender`).
- **How it works** (`crates/nv-core/src/editor_session.rs`, `Live`): the session keeps its own copy of the page doc (so the engine's tree never moves under it mid-call) bridged to the live page's doc with two update observers. The session's writes (origin `nv-editor`, the open's `nv-editor-load`, undo's) are queued and written into the live doc at the end of each call with origin `nv-editor-live:<n>` (one per session); nv-sync's observer sends and stores them like any local edit. Changes on the live doc not from this session's origin (the sync thread's, `LivePage::apply_update`'s, other sessions') are queued on whatever thread made them and merged (one `merge_updates_v1`) into the engine at the start of the next session call with origin `nv-editor-remote`, which carries the selection, isn't undoable and isn't forwarded back. So no echo either way, undo only takes back the session's own edits (yrs `UndoManager` on origin `nv-editor`), and task callbacks are unchanged. Observers are removed when the session drops. After `LivePage.close()` the session still works; its edits just aren't sent.
- **Core-owned lines touched** (own commit f1c6c37, **done by editor for core review**): `crates/nv-core/src/client.rs`, one crate-private accessor in a non-exported `impl LivePage` block: `pub(crate) fn doc(&self) -> &nv_model::yrs::Doc`. No behaviour change, nothing in the foreign API. This is the request below ("share the live doc"), first option.
- **One call per frame**: `view_render() -> ViewRender { revision, text_revision, view: ViewState, suggestion, focus_task_id, remote_cursors: [ViewCursor], can_undo, can_redo }` and `revision() -> u64`. `revision` moves on every call that may change what's drawn and when others' changes arrive; `text_revision` only when the text / line table changed. The view text is cached (keyed on the revision, checked against the tree), so the older view calls (`view_state`, `text_for_view`, `view_offset_to_pos`, `pos_to_view_offset`, `view_selection`, `replace_view_range`) stop rebuilding it too; they stay. For drawing, `view_render()` supersedes `view_state()` + `state()` + `can_undo/redo()` (EDITOR.md 10.1). Engine: `Editor::view_selection_in(&ViewText)`, `view_composition_in(&ViewText)`.
- **Tests** (`crates/nv-core/tests/editor_session.rs`, 14 → 17): `one_call_per_frame_and_revisions`; `a_live_session_edits_the_live_page_and_sees_others_changes` (against the stand-in collab server: typing is in the live page at once and on the server, the server's echo doesn't move the revision, a change made on the server reaches the session with the caret carried, undo takes back only the session's typing, `insertTask` goes through the callbacks and reaches the server, a second session on the box sees the first's edits and vice versa, the session survives `close()`); `a_live_session_needs_the_box`. Ratchet 232 unchanged.
- **Left**: `revision` is conservative (a call that changes nothing still moves it; `text_revision` is exact); remote changes arrive at the next session call, so the view needs the live page's `on_change` (or a timer) to redraw; untested on a device.

## 2026-11-21: native text-input contract, step 2 (branch `rewrite/editor-input`)

### Findings

- **Composition commits run input rules** in today's editor (TipTap's input rules also run on `compositionend`): `- ` committed through an IME makes a list. The engine does the same (commit types once with `insert_text`).
- **Replacements run input rules** in today's editor: ProseMirror reads the DOM change as typed text (`handleTextInput`), so an autocorrect or dictation correction can make a list. The contract says replacements don't; `input/replacement doesn't run input rules` is skipped on TipTap (README Findings).
- **Cancel over a selection deletes the selection** (Chromium deletes it when the composition starts); the engine now matches.
- Undo after a committed composition is one step on both. Undo after a replacement restores the text; TipTap's selection there is the replaced range (an artefact of how the runner selects it), so that scenario ignores the selection.

### Limits

- **Box fields** still read through `nv_model::Page::read` (no public fragment reader yet), so `open` only accepts `default` or a `box:<id>` that has geometry in `boxes` (`NoSuchBox` otherwise), and every read parses the whole page.
- **The session has its own doc**, not the `LivePage`'s: the app moves bytes between them (`live.apply_update(session.encode_update_since(sv))`, and `session.apply_update(...)` for others' changes). `PageListener::on_change` gives a `PageInfo`, not an update, so today the app would have to pass `live.document()` (the whole state; yrs ignores what it already has).
- Composition in a **task title** isn't shown (the title changes on commit). Undo/redo selections recorded before a remote change are clamped, not mapped. Sticky mapping falls back to clamping when the fragment holds something the tree drops (embeds inside text, unknown elements are handled).
- Undo grouping uses the wall clock (500 ms), so fast scripted input is one step.

### Requests

- **editor → core (nv-core):** share the live doc. The first is simpler; the session would then also need to hear remote changes (re-read on `on_doc_changed`).
- **editor → core (nv-model):** still the public fragment reader (`tree::read_fragment` or `Page::fragment(doc, name)`).
